## Resumen ejecutivo

El sistema está **gravemente roto en producción**. El chat, que aparentemente
"funcionaba", en realidad está congelado en estado "Conectando..." desde la
carga de cualquier página. Al disparar el flujo de análisis IA el backend
entra en estado de error 500 sostenido, arrastrando incluso endpoints que
no tienen relación directa con el análisis (lista de casos, debug de
documentos, creación de sesiones de chat).

Nivel de severidad global: **P0 — bloquea el producto entero**.

---

## CRITICAL (P0) — bloquean uso del producto

### C1. Análisis IA envenena el backend (reproducible)

Disparar un análisis con `POST /api/v1/analysis {"matter_id": 10}` deja los
siguientes endpoints respondiendo **500 Internal Server Error** de forma
permanente, hasta el momento de redactar este reporte (~4 minutos después):

| Endpoint | Antes del análisis | Después |
|---|---|---|
| `GET /api/v1/matters` | 200 | **500** |
| `GET /api/v1/matters/10` | 200 | **500** |
| `GET /api/v1/analysis/matters/10/status` | 200 `{"status":"new"}` | **500** |
| `GET /api/v1/analysis/matters/10/latest` | 200 `"No existe análisis"` | **500** |
| `GET /api/v1/alerts/matters/10` | 200 `[]` | **500** |
| `POST /api/v1/chat/sessions` | ? (no probado) | **500** |
| `GET /api/v1/documents/44/debug` | 500 | **500** |

El servidor sigue respondiendo (`/health` 200, `/auth/me` 200), por lo que
no es caída del proceso. Es un fallo de lógica/transacción a nivel de
servicio que **deja la BD o el ORM en estado inconsistente** y arrastra al
resto de rutas. Probable causa: el job de análisis corre dentro de
`BackgroundTasks` de FastAPI sin un worker real (el worker RQ de
`workers/document_processor` no se despliega, ver mem 4600) y, al fallar
o quedarse colgado, corrompe la sesión de BD o un lock global.

**Evidencia:** capturas `audit-dashboard-after-analysis-crash.png`,
`audit-floating-chat-stuck-connecting.png`, console `[ERROR] GET /api/v1/matters 500`,
Red de Playwright muestra el 500 sostenido.

### C2. Chat está congelado en estado "Conectando..."

El `Dialog` del chat flotante (presente en TODAS las páginas autenticadas)
muestra el placeholder `Conectando...` con el `textbox` y el botón de enviar
**deshabilitados desde la primera carga**. El endpoint
`POST /api/v1/chat/sessions` devuelve 500, así que el componente no puede
obtener el `sessionId` que necesita para habilitar el input.

Esto contradice la afirmación "el chat funciona". El chat **parecía**
funcionar porque la última respuesta se renderiza en la burbuja ("¡Hola!
Soy el asistente legal..."), pero ningún mensaje del usuario puede
salir. El usuario con el que probé sólo vería un chat que nunca responde.

### C3. Endpoint `/debug` de documentos → 500

El endpoint desplegado en el commit `c511cd6` para diagnosticar
documentos pegados **da 500 directamente** en `/api/v1/documents/44/debug`,
no 404. El cuerpo es `Internal Server Error` literal, sin cuerpo JSON
parseable, así que ni siquiera el cliente puede mostrar un hint útil.
El `/debug` no es operativo.

## HIGH (P1) — fallas que el usuario experimenta

### H1. Datos corruptos en `extracted_text`

Subí `apps/backend/laws/ley_proteccion_consumidor.pdf` (247 KB,
48 páginas). El backend lo marca como `status: "processed"` y devuelve un
`extracted_text` de 119 357 caracteres que **comienza con "Ley 18916 —
APRUEBA CODIGO AERONAUTICO"**. El filename y el contenido extraído son
de documentos distintos. Es el mismo bug documentado en la observación
mem 2796 (`extracted_text.encode()` en
`apps/backend/app/services/document_processor.py:157`). El análisis IA va
a operar sobre el texto del documento equivocado y, peor, se va a cachear
en el vector store.

**Acción:** corregir `document_processor.py:157` (probable uso de
`text.encode('utf-8', errors='replace')` que mezcla bytes con el PDF
anterior en memoria compartida). Verificar además que el `BytesIO` /
handle de PyMuPDF no se reuse entre requests.

### H2. La pestaña Tiempos pide una acción que no existe

La pestaña `Tiempos y Fechas Críticas` muestra el copy:

> Haz click en **"Buscar plazos en documentos"** para que la IA analice
> fechas críticas, multas, garantías y prescripciones.

Pero **no hay ningún botón con ese texto ni con ese aria-label** en el
DOM (`button[aria-label*="Buscar"]` = 0 resultados). Los plazos solo se
generan cuando se lanza un análisis desde la pestaña "Análisis IA". El
copy induce a error: el usuario va a Tiempos esperando actuar y no puede
hacer nada.

**Fix:** o (a) renderizar el botón que falta en Tiempos, apuntando a
`POST /api/v1/analysis` con el `matter_id` correspondiente y refetching
alerts al terminar, o (b) cambiar el copy a "Ejecuta un análisis desde la
pestaña Análisis IA para generar plazos automáticamente".

### H3. Subida de documento exige click manual en "Procesar"

Subir un archivo pasa a estado `uploaded` con un toast
"Documento subido exitosamente", pero **no se procesa hasta que el
usuario clickee manualmente el botón "Procesar"** que aparece al lado del
archivo. La mem 2837 decía que el procesamiento era automático vía
`BackgroundTasks`; la mem 2938 reportó que el botón "Procesar" no debería
aparecer. Hoy ambas cosas son ciertas: el botón sí aparece y, mientras
no se cliquee, el documento queda colgado en `uploaded`.

**Decisión a tomar:** (a) hacer el procesamiento realmente automático
(sin botón) — coherente con la mem 2837, **o** (b) si el botón se va a
quedar, eliminar el mensaje "Documento subido exitosamente" y reemplazarlo
por "Subido. Click Procesar para extraer texto y embeddings". La
ambigüedad actual es peor que cualquiera de las dos opciones.

## MEDIUM (P2) — UX rota, no impide funcionalidad

### M1. Dashboard muestra "0 casos" después de crear uno

`/dashboard` siempre reporta `Total casos: 0`, `En proceso: 0`,
`Listos para revisión: 0`, `Urgentes: 0`, y la sidebar dice
"Casos, 0 elementos". Aunque el caso 10 sí existe (confirmado por
`/api/v1/documents/matters/10/documents` que devuelve el documento).
**Hipótesis:** los contadores se alimentan de `GET /api/v1/matters`,
que ahora responde 500 por C1. Antes del análisis, los contadores
también estaban en 0 — probablemente un side effect del BFF o un cache
de SWR/RQ que no se invalida al crear un matter.

### M2. Sidebar muestra "0 elementos" en Casos (mismo origen que M1).

### M3. Error 404 desde `/api/v1/matters/10/deadlines`

El frontend potencialmente consulta `/api/v1/matters/{id}/deadlines`
(no verificado en la auditoría actual), pero la ruta correcta es
`/api/v1/alerts/matters/{id}` según OpenAPI. Si el cliente llama a la
URL equivocada, obtendrá 404 silencioso.

### M4. `/api/v1/precedents/search?q=...` → 0 resultados

`/precedents/search?q=proteccion+consumidor` devuelve
`{"results": [], "total": 0, "search_type": "keyword"}` en el tenant
nuevo (esperable: el seed no tiene precedentes para ese tenant). No es
un bug; es solo la verificación de que la ruta funciona.

## Plan de remediación propuesto

### Inmediato (P0) — antes de cualquier demo a usuario

1. **C1**: matar el `BackgroundTasks` de análisis y moverlo a un worker
   RQ real, o al menos blindarlo con un try/except que registre el error
   en `analysis_status.error` y libere el lock. El patrón actual
   rompe el backend entero; ver `app/services/analysis.py` y
   `apps/backend/app/api/endpoints/analysis.py`.
2. **C2**: arreglar `POST /chat/sessions`. Probable: una consulta a la
   tabla `matters` que se rompe porque el `matters` list está caído. Si
   `/chat/sessions` consulta `matters` por `matter_id`, y `matters` da
   500, el chat nunca arranca. Necesitamos aislar el chat del estado de
   matters (un chat sin matter debería poder crearse, modo Q&A libre).
3. **C3**: envolver el `/debug` en try/except y devolver siempre un
   JSON con la excepción (`{"error": str(e), "type": type(e).__name__}`)
   en lugar de propagar 500 sin cuerpo. El endpoint existe
   precisamente para diagnosticar — debe ser el más verboso del sistema.

### Corto plazo (P1)

4. **H1**: corregir `extracted_text.encode()` en
   `document_processor.py:157` y añadir un test que verifique que el
   texto extraído contiene el `original_filename` como substring.
5. **H2**: añadir botón "Buscar plazos" en la pestaña Tiempos, o
   reescribir el copy.
6. **H3**: eliminar la ambigüedad: o procesamiento automático o copy
   explícito.

### Observabilidad (P2)

7. Sustituir el cuerpo de error 500 (`Internal Server Error` literal)
   por un JSON con `{"detail": str(e), "request_id": "..."}` en TODOS
   los endpoints. Hoy es imposible diagnosticar nada sin ver los logs
   del servidor.
8. Añadir `/api/v1/health/deep` que verifique BD, Redis y Supabase
   Storage, no solo el proceso vivo.
