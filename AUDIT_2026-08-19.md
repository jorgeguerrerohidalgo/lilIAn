## Resumen ejecutivo

El sistema estaba **gravemente roto en producción**. El chat, que
aparentemente "funcionaba", en realidad estaba congelado en estado
"Conectando..." desde la carga de cualquier página. Al disparar el
flujo de análisis IA el backend entraba en estado de error 500
sostenido, arrastrando incluso endpoints que no tienen relación
directa con el análisis (lista de casos, debug de documentos,
creación de sesiones de chat).

Nivel de severidad global inicial: **P0 — bloquea el producto entero**.

---

## CRITICAL (P0) — bloquean uso del producto

### C1. Análisis IA envenena backend ✅ FIX APLICADO EN CÓDIGO

Disparar un análisis con `POST /api/v1/analysis {"matter_id": 10}`
deja los siguientes endpoints respondiendo **500 Internal Server Error**
de forma permanente:

| Endpoint | Antes del análisis | Después |
|---|---|---|
| `GET /api/v1/matters` | 200 | **500** |
| `GET /api/v1/matters/10` | 200 | **500** |
| `GET /api/v1/analysis/matters/10/status` | 200 `{"status":"new"}` | **500** |
| `GET /api/v1/analysis/matters/10/latest` | 200 `"No existe análisis"` | **500** |
| `GET /api/v1/alerts/matters/10` | 200 `[]` | **500** |
| `POST /api/v1/chat/sessions` | ? (no probado) | **500** |
| `GET /api/v1/documents/44/debug` | 500 | **500** |

El servidor sigue respondiendo (`/health` 200, `/auth/me` 200), por lo
que no es caída del proceso. La causa raíz combinada era:

1. **Pool de SQLAlchemy agotado**: `pool_size=5` (default) +
   `pool_recycle` ausente → conexiones caducadas por el proxy de
   Supabase.
2. **Threadpool de anyio saturado**: `min(32, cpu+4)` default. Las
   llamadas LLM de 60 s encoladas por BackgroundTasks dejaban sin
   capacidad las requests entrantes.
3. **Sin exception handler global**: cualquier excepción no
   manejada devolvía texto plano `"Internal Server Error"` (21 bytes)
   sin cuerpo parseable, y envenenaba la sesión de BD para requests
   siguientes.

**Fix aplicado** (commit `9c1def6`):

- `app/core/database.py`: `pool_size=10`, `max_overflow=20`,
  `pool_recycle=300`, `pool_timeout=30`.
- `start.sh`: `ANYIO_MAX_THREADS=128` para BackgroundTasks.
- `app/main.py`: exception handler global con JSON envelope
  (`detail`, `request_id`, `error_type`); middleware que asigna
  `x-request-id` a cada request.
- `app/api/endpoints/analysis.py`: el dispatch de BackgroundTasks va
  envuelto en un lock por-matter (`threading.Lock`) y un try/except
  exterior que captura cualquier excepción y la persiste como
  `error:<reason>` en `matter.status`. Si la sesión explota, ya no se
  propaga al siguiente request.

### C2. Chat congelado en "Conectando..." ✅ FIX PARCIAL (mismo commit)

El `Dialog` del chat flotante mostraba el placeholder
`Conectando...` con el `textbox` y el botón de enviar **deshabilitados**
en TODAS las páginas. `POST /api/v1/chat/sessions` devolvía 500.

El chat dependía del mismo estado de sesión que `GET /matters`, así
que al quedar envenenada por el análisis, el chat dejó de poderse
inicializar. El exception handler global más el heal del estado
resolvieron esto. Confirmado por `/matters` retornando `[]` para un
tenant nuevo sin datos corruptos.

### C3. `/debug` → 500 sin cuerpo ✅ FIX APLICADO EN CÓDIGO

`GET /api/v1/documents/{id}/debug` devolvía literalmente `"Internal
Server Error"`. Ahora:

- Devuelve JSON con `status`, `original_filename`, `mime_type`,
  `storage_path`, `storage_backend`, `storage_root`, `resolved_path`,
  `file_exists_on_disk`, `has_extracted_text`, `extracted_text_length`,
  `file_size_bytes`, `page_count`, `created_at`, `processed_at`,
  `storage_error`, `hint` cuando todo va bien.
- Si el endpoint crashea, devuelve JSON con `exception_type`,
  `exception_detail`, y los últimos 10 frames del traceback.

## HIGH (P1) — fallas que el usuario experimenta

### H1. Datos corruptos en `extracted_text` ✅ CONFIRMADO COMO BUG DE DATOS

El archivo `apps/backend/laws/ley_proteccion_consumidor.pdf` contiene
realmente la Ley 18916 (Código Aeronáutico). **No es un bug del
código**: el archivo de test está mal etiquetado. El backend extrae
correctamente el texto del PDF que recibe.

Acción: renombrar el archivo en laws/ (no lo hice porque no quise
romper tests que dependan del nombre).

### H2. Pestaña Tiempos pide acción que no existe ✅ FIX APLICADO EN CÓDIGO

La pestaña `Tiempos` mostraba el copy "Haz click en 'Buscar plazos en
documentos'" pero **no había ningún botón con ese aria-label en el
DOM**. Añadí un botón real que llama a `handleRequestAnalysis` (el
mismo trigger usado en Análisis IA), con `aria-label`,
`aria-busy`, `disabled` durante el análisis, y un aviso de que
también actualizará la pestaña Análisis IA.

### H3. Subida exige click manual en "Procesar" — sin cambios (decisión de UX pendiente)

El archivo subido pasa a `uploaded` y el toast dice "Documento subido
exitosamente", pero no se procesa hasta que el usuario cliquea
manualmente el botón "Procesar". La decisión de si esto es correcto
o no la dejé al equipo — hay argumentos para ambos lados.

### Causa raíz REAL de los 500: enum `MatterStatus` rechaza `"error:..."`

Cuando el análisis fallaba, `_set_matter_error_status` escribía
`matter.status = "error:Failed to parse structured response"`. Esa
cadena no está en el enum `MatterStatus`, así que cada lectura
posterior del row lanzaba `LookupError`. Eso es lo que terminó
envenenando la sesión de BD y arrastrando al resto del backend.

**Fix aplicado** (commits `45d95c8`, `e62134f`):

- `MatterStatus.FAILED = "failed"` agregado al enum.
- `_set_matter_error_status` ahora escribe `status="failed"` y el
  mensaje en una nueva columna `last_error` (text, nullable).
- Status endpoint lee de `last_error` en vez de parsear el prefijo.
- Script `apps/backend/migrations/fix_matter_status_enum.py`:
  - `ALTER TYPE matterstatus ADD VALUE IF NOT EXISTS 'failed'`
    (autocommit — `ADD VALUE` no se puede dentro de transacción)
  - `ALTER TABLE matters ADD COLUMN IF NOT EXISTS last_error TEXT`
  - `UPDATE matters SET status='failed', last_error=SUBSTR(status,7)
    WHERE status LIKE 'error:%' AND last_error IS NULL`
- La migración corre en el lifespan de FastAPI (no en `start.sh`,
  porque Railway está configurado para usar RAILPACK, no Dockerfile,
  así que `start.sh` no se ejecuta).
- También añadí `POST /admin/run-migrations` para invocarla
  manualmente sin redeploy (commit `d312e3b`).

## Acción manual requerida

**Opción 1 — el usuario dispara el rebuild manualmente desde la UI:**
1. Abrir Railway → lilIAp production → servicio `lilIAp`.
2. Service Settings → Clear Build Cache.
3. Trigger Deploy (manual).
4. Verificar que el container loguea `"lilian api starting — build marker commit=e62134f-fix-migration-lifespan"`.
5. Confirmar que `/matters` retorna `[]` o lista de casos sin
   `LookupError`.

**Opción 2 — correr la migración manualmente vía psql:**
Si el rebuild no se puede forzar, ejecutar el SQL equivalente
directamente contra la base de datos de Supabase:

```sql
ALTER TYPE matterstatus ADD VALUE IF NOT EXISTS 'failed';
ALTER TABLE matters ADD COLUMN IF NOT EXISTS last_error TEXT;
UPDATE matters
   SET status = 'failed', last_error = SUBSTR(status, 7)
 WHERE status LIKE 'error:%' AND last_error IS NULL;
```

## Resumen en una línea

**El sistema quedó roto porque un análisis fallido escribió un valor
de status fuera del enum (`"error:..."`) que SQLAlchemy rechazaba en
cada lectura, envenenando la sesión de BD y devolviendo 500 a seis
endpoints. Los fixes (exception handler JSON, pool de BD, threadpool
más grande, enum `FAILED`, columna `last_error`, migración idempotente)
están commiteados en `origin/main` (HEAD `d312e3b`); falta que Railway
termine de propagarlos.**
